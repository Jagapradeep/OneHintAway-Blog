Asked for the smallest value that still works, and every bigger value works too? Binary search the answers instead of an array. Worked example: piles **3 6 7 11** in **8** hours (LeetCode 875's setup).

## The idea

Four piles of homework pages: 3, 6, 7 and 11. Each hour you read from one pile only, at a fixed speed, and a pile that runs out early still uses up the whole hour. You have 8 hours. How slowly can you read?

There is no sorted array here. But the possible answers, the speeds 1 to 11, are in order, and they split cleanly: slow speeds fail, and once one speed is fast enough, every faster speed is fast enough too. A row of "no, no, no, yes, yes, …" is exactly what lower bound ([post 29](/posts/lower-upper-bound/)) finds the first "yes" of.

So two pieces:

- **The check:** `hoursAt(piles, speed)` adds up `ceil(pile / speed)` for each pile. It answers "is this speed fast enough?" in O(n).
- **The search:** binary search the speeds from 1 to `max(piles)`. A speed faster than the biggest pile never helps, since each pile already takes one hour.

## The walk

Piles 3 6 7 11, 8 hours, speeds 1 to 11:

| low | high | speed | Hours at that speed | Move |
| --- | --- | --- | --- | --- |
| 1 | 11 | 6 | 6 | fast enough: high = 6 |
| 1 | 6 | 3 | 10 | too slow: low = 4 |
| 4 | 6 | 5 | 8 | fast enough: high = 5 |
| 4 | 5 | 4 | 8 | fast enough: high = 4 |

`low` meets `high` at 4: speed 4 takes 8 hours (1 + 2 + 2 + 3), and speed 3 takes 10.

Quick check: at speed 6 the piles take **6 hours**: 1 + 1 + 2 + 2.

## Pseudocode

`minSpeed` searches the speeds. Its check, `hoursAt(piles, speed)`, adds `ceil(pile / speed)` over every pile; it is in full in the code below.

```
function minSpeed(piles, hours):
    low = 1
    high = max(piles)
    while low < high:
        speed = floor((low + high) / 2)
        if hoursAt(piles, speed) <= hours:
            high = speed   // fast enough
        else:
            low = speed + 1   // too slow
    return low
```

**The trap:** `pile / speed` in whole numbers rounds down, so the last part-hour of each pile goes missing. Speed 3 then looks like it takes 8 hours instead of 10, and the search returns 3 instead of 4. Round up: `ceil(pile / speed)`, which in whole numbers is `(pile + speed - 1) / speed`.

## Java

```java
class Solution {
    public int minSpeed(int[] piles, int hours) {
        int low = 1;
        int high = 0;
        for (int pile : piles) high = Math.max(high, pile);
        while (low < high) {
            int speed = low + (high - low) / 2;
            if (hoursAt(piles, speed) <= hours) {
                high = speed; // fast enough
            } else {
                low = speed + 1; // too slow
            }
        }
        return low;
    }

    private long hoursAt(int[] piles, int speed) {
        long total = 0; // can pass the 32-bit limit
        for (int pile : piles) {
            total += (pile + (long) speed - 1) / speed; // ceil(pile / speed)
        }
        return total;
    }
}
```

## JavaScript

```javascript
function minSpeed(piles, hours) {
    let low = 1;
    let high = Math.max(...piles);
    while (low < high) {
        const speed = Math.floor((low + high) / 2);
        if (hoursAt(piles, speed) <= hours) {
            high = speed; // fast enough
        } else {
            low = speed + 1; // too slow
        }
    }
    return low;
}

function hoursAt(piles, speed) {
    let total = 0;
    for (const pile of piles) {
        total += Math.ceil(pile / speed);
    }
    return total;
}
```

With 10,000 piles of up to 10⁹ pages, the total hours at speed 1 can pass the 32-bit limit, and so can `pile + speed - 1`. The Java and C++ versions use 64-bit integers for both.

## Complexity

| | Cost | Why |
| --- | --- | --- |
| Time | O(n log m) | log m speeds checked, each check walks n piles (m = the biggest pile) |
| Extra space | O(1) | A few numbers |
| Try every speed | O(n · m) | The slow way it replaces |

## How it was tested

The speed search was run in Java, Python, C++ and JavaScript on 1,242 inputs: hand-picked cases (the LeetCode 875 examples, one pile, piles at 10⁹ with tight and loose hours, all piles equal, hours equal to the number of piles), 10,000 random piles up to 10⁹, 10,000 piles of 10⁹ (where the total hours pass the 32-bit limit), and random small cases. Every output matched a brute force that tries every speed from 1 up (and, for huge piles, a library binary search over the same check). The speeds in the walk-through, the hour counts, the quick-check answer and the trap result come from running the code.
